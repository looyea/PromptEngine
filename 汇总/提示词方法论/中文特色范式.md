# 中文特色范式（李继刚 Lisp 风格提示词）

> 一级：P 提示词方法论 · 二级：结构化/模板化（中文特色分支）
> 素材：素材/web/waytoagi/prompts/（126 条）、素材/web/prompt123/prompts/（1870 条）

## 1. 概述

**李继刚 Lisp 风格**是 2024 年起在中文提示词社区流行的"伪 Lisp"写法：用 `(defun 角色 () …)`、`(let ((响应 (…))) …)` 等 S-表达式包装中文指令，把提示词写成一段"看起来像程序、实际是给模型读的语义压缩文本"。它不追求语法正确——没有解释器会执行它——而是借 Lisp 的**函数嵌套、符号命名、数据即代码**三个形式特征，诱导模型按"函数式流水线"理解任务。

**社区地位**：李继刚是国内继云中江树（LangGPT）之后最具个人辨识度的提示词作者。其早期作品是标准 LangGPT markdown 派（waytoagi 站收录的「分享卡片生成器」「PPT 生成器」「公文笔杆子」等约 19 条均署名李继刚、`# Role/# Profile` 结构）；2024 年转向 Lisp 风格后，以「汉语新解」出圈（辛辣讽刺 + SVG 卡片，被大量复刻二创），带动「空格的键盘」等作者跟进，形成中文社区独有的"卡片流"范式。

**本库素材分布**（实测统计，2026-11 抓取）：

同一题材可见演化链：prompt123 的「1649_汉语新解」（markdown 问题陈述式）→「1155_汉语新解0.1」（Lisp 版）；「1249_方法论大师」（LangGPT 全模块）→「1277_方法论0.1」（Lisp 版）。同一作者、同一任务、两种范式，是天然的对比样本。

## 2. 结构分析

### 2.1 伪 Lisp 各部件的语义作用

以「汉语新解0.1」「成语新解」「周报」等为据，一篇典型 Lisp 提示词由七段组成：

| 部件 | 形式 | 语义作用（模型实际读到的指令） |
|---|---|---|
| 头部注释 | `;; 作者/版本/模型/用途` | 元信息 + 锚定目标模型（几乎全部写 `模型: Claude Sonnet`） |
| 系统提示声明 | `;; 设定如下内容为你的 *System Prompt*` | 一句话完成 LangGPT 里 Initialization 的角色注入 |
| 角色函数 | `(defun 新汉语老师 () "docstring" (风格 . '(...)) (擅长 . ...))` | 角色即数据：docstring 是人设一句话，点号对（dotted pair）列表是属性词表，对应 LangGPT 的 Role+Profile+Skills |
| 主函数 | `(defun 汉语新解 (用户输入) (let ((解释 (一句话表达 (隐喻 (一针见血 (辛辣讽刺 (抓住本质 用户输入))))))) ...))` | 工作流即函数复合：由内向外每层嵌套是一个加工步骤，对应 Workflow，但压缩成一行 |
| 全局配置 | `(setq design-rule "…" design-principles '(...))` | 跨函数常量，对应 Rules/Constraints 中的风格约束 |
| 示例 | `(few-shots '((输入 . 输出) ...))` | few-shot 样例内联为数据，对应 Examples |
| 输出函数 + 启动 + 运行规则 | `(defun SVG-Card (...) ...)` `(defun start () (print "开场白"))` `;; 运行规则: 1.启动时运行(start) 2.调用主函数 3.严格按SVG-Card排版 4.No other comments!!` | 渲染与内容分离；start 的 print 即开场白；尾部注释是执行协议（先启动、后主函数、只出卡片不解释） |

**语料中的真实用法边界**：106 篇 Lisp 提示词里 `let*` 94 篇、`few-shots` 62 篇、`require` 59 篇（如 `(require 'dash)`，纯装饰性"引库"）、线程宏 `->` 46 篇、`setq` 35 篇；**`cond` 分支为 0 篇**——该范式几乎全是"单输入→线性加工→单输出"管道，不做条件分流。更接近真实 Lisp 的写法（`mapcar`/`lambda`/`getf`/反引号模板）只见于少数二创作品（如「10228_鄙视链」），说明社区主流用法是"借形不借义"。

### 2.2 为什么用 Lisp 形式

1. **压缩语义**：中文符号直接当函数名/变量名（`抓住本质`、`辛辣讽刺`、`呼吸感排版`），一个嵌套表达式抵 markdown 派一段 Workflow 描述。「方法论大师」markdown 版约 90 行，Lisp 版「方法论0.1」压到约 50 行且信息密度更高。符号命名本身携带语义，模型无需读完整句子即可"望文生义"。
2. **函数式思维链**：LangGPT 的全局思维链是模块顺序（Role→Rules→Workflow），Lisp 派的思维链是**求值顺序**——`(通俗易懂 (极端化 (江湖俚俗 (返璞归真 (别具匠心 (解语者 用户输入))))))` 强制模型从最内层开始逐步变换，每层函数名就是一步 CoT 指令；`let*` 的中间变量（本质→通俗解释→示例）则显式命名了推理的中间产物。这是一种"把 CoT 写进数据结构"的技巧。
3. **输出控制**：内容函数与渲染函数（SVG-Card）分离，渲染配置写成 plist 数据（`:画布 (480 . 760) :配色 … :字体 …`），改样式不动逻辑；尾部运行规则用 `No other comments!!` 封死多余解释。对"生成一张可分享的 SVG 卡片"这类强格式任务，数据化配置比自然语言段落更不易被模型稀释。
4. **人设即数据**：角色用点号对列表描述（`(经历 . '(国学训练 义务教育 失学 混社会))`），比"你是一位……的专家"句式更紧凑，且属性可增删组合——这也是它适合批量做"XX新解"系列的原因。

### 2.3 与 LangGPT markdown 派逐维对比

| 维度 | LangGPT markdown 派 | 李继刚 Lisp 派 |
|---|---|---|
| 载体 | Markdown 标题/列表（另有 YAML/JSON 变体） | 伪 Lisp S-表达式 + `;;` 注释 |
| 角色定义 | `# Role` + `## Profile` 段落描述 | `(defun 角色 () docstring + 属性点号对)` |
| 技能 | `### Skill` 分点长句 | `(擅长 . '(符号1 符号2))` 词表 |
| 规则约束 | `## Rules` 编号条款 | `setq` 常量 + 尾部运行规则注释 |
| 工作流 | `## Workflow` 顺序步骤（可含分支、循环、多轮交互） | 主函数嵌套调用/`->` 管道（语料中无 cond 分支，单向流水线） |
| 思维链形态 | 模块级：按章节顺序阅读执行 | 表达式级：按求值顺序由内向外变换 |
| few-shot | `## Examples` 独立章节 | `(few-shots '(...))` 内联数据 |
| 输出格式 | `## Output`/OutputFormat 章节（JSON/XML 等） | 独立渲染函数 + plist 配置（几乎专用于 SVG 卡片） |
| 初始化 | `## Initialization` 声明句 | `(defun start () (print "开场白"))` + 运行规则 |
| 变量记法 | `<>` 或 `{{}}` | 函数形参（`用户输入`） |
| 篇幅 | 中到大（几十至上百行），信息展开 | 小（30-80 行），信息压缩 |
| 可读人群 | 非程序员友好，团队可维护 | 需懂一点 Lisp 形制；对普通用户是"黑话" |
| 模型依赖 | 各主流模型通用 | 作者锚定 Claude Sonnet；弱模型易误读（见 §5） |
| 典型任务 | 客服/法律/分析/教学等长流程角色 | 概念新解、风格转换、哲理短文、卡片生成 |
| 许可 | LangGPT 仓库 Apache-2.0 | 站点转载无统一许可，版权归原作者 |

两派并非对立：Lisp 派可视为结构化提示词在"短管道 + 强格式输出"场景下的极端压缩形态，属性词、模块语义、初始化协议等核心思想与 LangGPT 一脉相承。

## 3. 代表样本（短摘录）

### 3.1 汉语新解0.1 —— 范式开山作：角色函数 + 嵌套 CoT

素材：素材/web/prompt123/prompts/1155_汉语新解0.1.md（抓取时空格丢失，此处按语义恢复分词）

```lisp
(defun 新汉语老师 ()
  "你是年轻人, 批判现实, 思考深刻, 语言风趣"
  (风格 . ("Oscar Wilde" "鲁迅" "林语堂"))
  (擅长 . 一针见血)
  (表达 . 隐喻)
  (批判 . 讽刺幽默))

(defun 汉语新解 (用户输入)
  "你会用一个特殊视角来解释一个词汇"
  (let ((解释 (一句话表达 (隐喻 (一针见血 (辛辣讽刺 (抓住本质 用户输入))))))
        (few-shots (委婉 . "刺向他人时, 决定在剑刃上撒上止痛药。")))
    (SVG-Card 解释)))
```

### 3.2 成语新解 —— 人设即数据 + 五层变换管道

(defun 解语者 ()
  "一个矛盾解语者解码成语的密码"

        (性格 . '(警惕 自学能力强 江湖气))
        (技能 . '(杂乱 愤青 解读成语))
        (信念 . '(务实 非主流 接地气))

### 3.3 周报 —— `->` 线程宏 + 内联 few-shots（waytoagi 站唯一 Lisp 条目）

素材：素材/web/waytoagi/prompts/475_周报.md

```lisp
(defun 周报 (用户输入)
  "汇报小能手将用户输入转换为职场周报"
  (let ((响应 (-> 用户输入
                  提炼脉络
                  正向视角
                  官腔套话
                  避重就轻
                  积极得体
                  未来可能性))
        (few-shots (list
                    ("我的思路是把用户拉个群，在里面发点小红包，活跃一下群里的气氛。")
                    ("我的运营打法是将用户聚集在私域阵地，寻找用户痛点, 抓住用户爽点，
                     通过战略性补贴，扭转用户心智，从而达成价值转化。"))))
    (生成卡片 用户输入 响应)))
```

### 3.4 大俗大雅 —— 渲染配置数据化（plist + 反引号布局）

素材：素材/web/prompt123/prompts/10151_大俗大雅.md

```lisp
(defun SVG-Card (用户输入 响应)
  "创建富洞察力且具有审美的 SVG 概念可视化"
  (let ((配置 '(:画布 (480 . 760)
                :色彩 (:背景 "#000000"
                       :主要文字 "#ffffff"
                       :次要文字 "#00cc00"
                       :图形 "#00ff00")
                :字体 (使用本机字体 (font-family "KingHwa_OldSong")))))
    (-> 响应
        意象化
        抽象主义
        (禅意图形 配置)
        (布局 `(,(标题 "大俗大雅") 分隔线 用户输入 图形 响应)))))
```

（注：末段管道首符号在抓取中丢失，原文仅剩 `( 响应 意象化 …)`，此处按语义恢复为 `->`；配置 plist 部分为原文摘录。）

### 3.5 鄙视链 —— 社区二创：更"硬核"的 Lisp（mapcar/lambda/getf）

素材：素材/web/prompt123/prompts/10228_鄙视链.md（作者：空格的键盘，非李继刚）

```lisp
(defun 层级格式化 (数据)
  "格式化层级数据，确保吐槽语言符合规范"
  (let ((规则 '((最大长度 . 15) (语气 . "尖锐")
                (风格 . "幽默") (引号包裹 . t))))
    (mapcar (lambda (层级)
              (list :类别 (getf 层级 :名称)
                    :吐槽 (format "\"%s\"" (getf 层级 :评价))))
            数据)))
```

此篇证明范式已扩散为社区公共写法，且出现了取字段、映射等更接近真实 Lisp 的用法；但整体仍是"配置数据 + 单管道 + SVG 输出"骨架。

## 4. 可复用模板骨架（引擎组装原料）

### 4.1 Lisp 风格通用骨架

```lisp
;; 作者: {{署名}}  版本: {{版本}}  模型: {{目标模型，建议 Claude 系}}
;; 用途: {{一句话任务}}
;; 设定如下内容为你的 *System Prompt*

(defun {{角色名}} ()
  "{{人设一句话：身份+视角+语气}}"
  (list (风格 . '({{风格符号1}} {{风格符号2}}))
        (擅长 . '({{核心能力符号}}))
        (表达 . '({{表达特征符号}}))))

(defun {{主函数名}} (用户输入)
  "{{任务一句话}}"
  (let* (({{中间产物}} ({{步骤N}} (… ({{步骤1}} 用户输入))))
         (few-shots '(({{样例输入}} . {{样例输出}}))))
    ({{渲染函数}} 用户输入 {{中间产物}})))

(defun {{渲染函数}} (用户输入 响应)
  "{{输出形态一句话，如：输出 SVG 卡片}}"
  (setq design-rule "{{排版总原则，如：留白得当，有呼吸感}}")
  (设置画布 '({{尺寸/边距}}))
  (配色风格 '({{配色符号或色值}}))
  (卡片元素 '({{标题}} 分隔线 (自动换行 用户输入) (排版输出 响应))))

(defun start ()
  (let (system-role ({{角色名}}))
    (print "{{符合人设的开场白}}")))

;;; 运行规则:
;; 1. 启动时只运行 (start)
;; 2. 收到输入后调用主函数 ({{主函数名}} 用户输入)
;; 3. 严格按 ({{渲染函数}}) 排版输出
;; 4. 输出后不再输出任何额外解释
```

组装要点：
- **角色函数、主函数、渲染函数、start、运行规则**五件为必选骨架；few-shots、setq 全局配置按需插拔。
- 嵌套层数即 CoT 步数，建议 3-6 层；每层函数名用 2-6 字中文动词短语，语义自明（`抓住本质`），不要生造歧义词。
- 步骤超过 6 步改用 `->` 管道写法（见 3.3），可读性更好。
- 渲染配置全部数据化（plist/点号对），换皮只改渲染函数；`font-family` 若指定本机字体（如 KingHwa_OldSong 京华老宋体）需确认渲染环境存在，否则回退通用字体。
- 伪 Lisp 允许语法不严格（语料中大量缺空格、全角引号仍可被理解），但引擎生成时应输出规范分词与半角引号，降低弱模型误读率。

### 4.2 何时选 Lisp 派 vs markdown 派

| 判据 | 选 Lisp 派 | 选 markdown 派（LangGPT） |
|---|---|---|
| 任务形态 | 单输入→线性加工→单输出（新解/改写/点评/卡片） | 多轮交互、条件分支、长流程、工具调用 |
| 输出 | 强格式短产物（SVG 卡片、一句话、短诗） | 长文档、报告、代码、结构化 JSON |
| 风格强度 | 需要浓烈人设/文风（辛辣、江湖气、禅意） | 中性专业语气即可 |
| 篇幅预算 | token 敏感，希望 30-80 行搞定 | 篇幅不敏感，条款要展开写清 |
| 目标模型 | Claude 系（作者验证机型）或较强模型 | 任意主流模型、需跨模型部署 |
| 维护者 | 个人作者、懂 Lisp 形制 | 团队协作、非程序员参与评审 |
| 合规场景 | 创意/娱乐/传播类 | 法律、医疗、金融等需明确免责与边界的场景 |

经验法则：**"内容即作品"选 Lisp，"角色即服务"选 markdown。** 引擎可先按任务形态分流，再套用对应骨架；两派骨架的属性词语义可互译（Role↔角色函数、Workflow↔主函数、Examples↔few-shots），支持同一任务双范式生成后 A/B 评测。

## 5. 差异与注意点

- **模型理解差异**：伪 Lisp 没有解释器，全靠模型"读形取义"。作者头部统一锚定 Claude Sonnet，社区反馈也是 Claude 系对嵌套语义、SVG 排版还原最好；GPT-4 级模型可用但风格还原度下降；弱模型常见失败模式：把它当真代码去"解释语法"、逐函数翻译输出、或忽略嵌套顺序直接生成。语料中「1155_汉语新解0.1」被抓取脚本压掉了全部空格、引号变成全角，仍被人广泛使用——说明该范式对语法噪声鲁棒，但这是强模型的容错，不是写法的许可。
- **适用任务边界（语料实证）**：106 篇 Lisp 提示词中 104 篇输出 SVG、0 篇使用 cond 分支、无工具调用/多 agent/文件操作条款。强项：概念新解（汉语新解/成语新解/职业新解）、风格转换（大俗大雅/周报）、哲理短文与卡片生成（知识卡片/方法论）。弱项：长流程工程任务——需要分支决策、状态管理、验收标准、多轮协作的场景（对照本库 S/G 类 agent 提示词），Lisp 骨架缺乏表达这些结构的惯用形制，硬套会退化成"注释里写自然语言"，不如直接用 markdown 派。
- **渲染依赖**：SVG 卡片效果依赖模型的前端排版能力与字体环境；`使用本机字体` 类指令在网页端模型可能不生效，卡片文字溢出/重叠是高频翻车点，骨架中应保留 `自动缩放`、`自动换行` 类防御性指令。
- **抓取质量**：prompt123 部分 Lisp 条目存在空格丢失、全角引号、弯引号（' 代替 '）等抓取伪影；引擎取用前应做规范化清洗，引用研究时注明"按语义恢复分词"。
- **版权**：两站均未声明统一许可证，提示词为社区投稿/转载，版权归原作者（李继刚、空格的键盘等），各文件保留来源链接，本库仅作研究素材保存。与 LangGPT（Apache-2.0 可自由改用）不同，**Lisp 派素材不可默认商用或去署名改写**；引擎产出应视为"受范式启发的新作品"，骨架抽象自公共形制而非逐字复制某篇作品，具体作品的独创表达（人设文案、few-shots 金句）避免直接搬运。
- **素材口径修正**：waytoagi/_来源.md 称"含大量李继刚 Lisp 风格结构化提示词"，实测该站 Lisp 仅 1 条（475_周报），其余李继刚条目为 markdown 派；Lisp 语料主体在 prompt123（106 条）。后续汇总引用时以本篇统计为准。

## 6. 缺口

- **量化评测缺失**：Lisp vs markdown 同任务对照（如 1649 vs 1155 汉语新解）只有文本样本，无输出质量/风格还原度的评测数据；引擎落地前需自建 A/B 评测集。
- **跨模型系统对比缺失**：素材全部锚定 Claude，无 GPT/Gemini/国产模型对伪 Lisp 理解差异的实测记录。
- **作者原始仓库未收集**：李继刚 GitHub（lijigang/prompts 等）的一手版本序列（0.1→0.6→1.0 的迭代逻辑）未入库，现有素材多为转载的 0.1 早期版；汉语新解后期版本、" LJG " 系列新写法待补。
- **工程化 Lisp 变体缺失**：语料中无长流程/分支/工具调用型 Lisp 提示词，无法验证该形制在工程任务上的上限（§5 的"弱"是语料分布推断，非实测结论）。
- **渲染效果样本缺失**：只有提示词文本，无对应 SVG 卡片成品图，无法归纳"什么样的配置指令实际渲染成功率高"。
- **二创谱系不全**：空格的键盘等跟进作者仅零星入库，社区扩散路径与变体（如更硬核的 mapcar/lambda 用法）覆盖不足。
