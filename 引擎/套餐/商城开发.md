# 套餐：电商商城开发（含后台管理）

> 用途：引擎模式 B2 的套餐脚本。一次业务对象访谈 → 共享上下文卡 → 交付 7 条按阶段排列的提示词（提示词包本身就是最终交付物：客户拿着它逐条喂给编码 agent/LLM，即可自动产出商城网站）。
> 骨架来源：汇总/软件开发/Spec驱动开发.md（链结构）、汇总/软件开发/编码规约.md（文件写入约定）、汇总/B2B商业/产品与运营.md（需求分层）、汇总/游戏/工作流与验收.md（阶段门与测试证据分级，模式通用）。
> 完备度标尺：本域的 游戏Spec01.md 位＝文末「硬规格锚」节（依 ENGINE.md 规格饱满模块 v0.8 增设）——交付前逐行对照走查，任一维度只有原则、没有数值/清单/可判是·否条目的，视为壳节回炉。
> 范式说明：任何行业的套餐都照本结构扩展——**业务对象问卷 + 上下文卡 + 分阶段提示词包 + 兼容规则**（教育=课程/学员/排期，内容站=栏目/发布流，预约类=资源/时段/履约）。

## 第一阶段：业务对象问卷（逐项形成上下文卡）

| 组 | 问题 | 选项 | 联动/兼容规则 |
|---|---|---|---|
| 形态 | 卖什么？ | **实物 B2C** / 数字商品 / 订阅制 / 二手 C2C / 多商家入驻 | 数字商品→删物流组，库存规则简化为授权制(R1)；订阅制→订单状态机加计费周期/续费/取消(R2)；多商家→全表加"店铺"维度+分账佣金+后台扩角色，复杂度跳档，建议二期(R3) |
| 商品 | 品类与商品结构？ | 单级分类 / **两级分类树** / 多级(>3 慎用)；有无规格矩阵（颜色×尺寸=SKU） | 有规格→商品/库存/购物车/订单四张表全要 SKU 维度；无规格→简化为商品级库存 |
| 商品 | 特殊品类规则？ | 无 / 需资质（食品/医疗/酒类）/ 需年龄门槛 / 限购 | 资质品类→商家资质与商品审核两条流程提示词（追加），法务合规免责条款注入 |
| 价格 | 促销玩法？ | 无 / 优惠券 / 秒杀 / 会员价 / 组合套餐 | 券+秒杀可叠加→必须追问**叠加与结算优先级**规则，否则订单金额计算无法验收(R4) |
| 用户 | 登录与会员？ | 手机验证码 / 微信授权 / 邮箱；是否分级 | 小程序形态→登录方式受平台限制(R5) |
| 订单 | 售后与履约？ | 仅退款/退货退款/换货；拆单发货？ | 拆单→订单-包裹两级状态机，复杂度↑，标注 `[假设：不拆单]` 为默认 |
| 支付 | 渠道？ | 微信支付 / 支付宝 / Stripe / PayPal | 只问渠道不问密钥；提示：支付资质与备付金合规需另行确认（免责条款）；小程序内只能用微信(R5) |
| 后台 | 角色与权限？ | 老板 / 运营 / 客服 / 财务 四岗默认 | 多商家(R3)时加"商家"角色与数据隔离规则 |
| 技术 | 端与栈？ | Web(Next.js/纯前端) / 微信小程序 / App；有无指定栈 | 客户不懂→给推荐并写进 DECISIONS 条款；小程序→前端提示词换 WXML 语境(R5) |

## 兼容规则汇总（访谈时当场执行）

- R1 数字商品：删物流组与运费模板；"库存"改授权制，秒杀逻辑简化。
- R2 订阅制：订单状态机追加重费/宽限/取消退款分支；支付提示词加扣款失败重试策略。
- R3 多商家：触发全链复杂度告警，建议拆两期；分账合规免责注入 #3/#6。
- R4 促销叠加：未定义叠加规则前，#6 拒绝生成金额计算逻辑，先回访谈。
- R5 小程序：登录/支付/前端技术栈三处联动改写；违反时当场提示不可选。
- R6 资质品类：追加"商家资质审核"提示词（第 8 条），法务免责条款强制。

## 硬规格锚（本域的 游戏Spec01 位：完备交付物应长什么样）

游戏域有 游戏Spec01.md 当完备度标尺，商城域此前没有——下表即补上的标尺：交付的每条提示词产物（spec/schema/api-spec/页面/测试）按维度写到这个密度才算"肉长满了"，凡留给执行机器自决的，给方向列表+决策判据而非空格（ENGINE.md 规格饱满模块第 2 条）。数值是规范性起点值，可被上下文卡覆写，但不可空置。

| 维度 | 必须达到的具体项（硬数值/枚举清单） | 依据 |
|---|---|---|
| 商品模型 | schema.sql 逐表列字段：SPU ≥12 字段（标题/类目ID/品牌/主图/详情图集/富文本详情/单位/状态/销量/SEO 标题/关键词/创建与更新时间），SKU ≥8 字段（规格组合/售价/划线价/库存/图/条码/状态/SKU 编码）；每列带业务含义行内注释、join 关系显式声明；规格矩阵示例 ≥2×2=4 个 SKU 实例行 | 汇总/数据/text-to-SQL.md §2 第 1 条（注释即语义）；本套餐商品组 |
| 库存扣减并发 | DECISIONS.md 比较 ≥2 方案（如 DB 乐观锁版本号 UPDATE…WHERE version=? vs 预扣+TTL 预留令牌/Redis 原子扣减），各写适用规模、失败模式、选中理由；验收=并发压测脚本可判是/否：100 并发抢 10 件库存，超卖=0、负库存=0 | ENGINE.md 规格饱满模块第 2 条（自决给方向+判据）；汇总/游戏/工作流与验收.md（测试证据分级，本套餐 #6/#7 引用） |

完备样例一段（库存扣减一节，写完 vs 没写完）——示意，数值随客户上下文覆写：

- **写完**（游戏Spec01.md 第四节那种密度）："库存扣减用乐观锁：skus 表带 version 列，SQL=`UPDATE skus SET stock=stock-#{n}, version=version+1 WHERE id=#{id} AND stock>=#{n} AND version=#{ver}`；影响行数 0 视为冲突，重试 ≤3 次后失败并提示'手慢了'。验收：100 并发抢 10 件库存压测脚本，成功恰好 10 单、超卖 0、负库存 0，压测输出截图存 PROGRESS.md。"
- **没写完**（只有原则的空话，回炉）："库存系统要保证数据一致性和并发安全，防止超卖。"
- 差别在前者有数值、有 SQL、有比较过的方案、有可判是/否的压测；后者执行机器没东西可吃。
