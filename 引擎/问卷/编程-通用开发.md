# 问卷：编程 · 通用开发（给编码 agent / LLM 的开发提示词）

> 用途：引擎模式 B1 的访谈脚本。问完→汇总槽位确认→走模式 A 组装；核心分岔在 Q2 交付形态（单提示词 / Spec 链 / mega-spec / agent 系统提示词）。
> 组装原料：汇总/软件开发/编码规约.md（§4 单条规约骨架）、汇总/软件开发/Spec驱动开发.md（§4 specify→clarify→plan→tasks→implement→analyze 链 + constitution）、汇总/软件开发/Agent系统提示词.md（§4 十模块系统提示词骨架）。
> 访谈纪律（ENGINE.md B1）：一轮 1-3 题；每题给选项+推荐值+一句人话解释；客户可说"都用默认"跳到终态——触发 ⚠️ 缺口的题必须解释后由客户拍板。

## 访谈题序（一轮 1-3 题，客户可说"都用默认"跳到终态）

| # | 问题 | 选项（推荐值加粗） | 槽位 | 联动 |
|---|---|---|---|---|
| Q1 | 这次要 AI 干什么类型的活？ | **新功能开发** / 修 bug / 重构 / 写测试 / 代码审查 / 解释代码 | task_type | 写测试/代码审查/重构 → 执行 R6 缺口提示；修 bug → 按"期望-实际-环境"三要素排障式收集信息（编码规约.md §2，同 数据分析与科学.md §3.4 纠错式） |
| Q2 | 交付形态（提示词长什么样）？ | 单条任务提示词 / **Spec 链（specify→clarify→plan→tasks→implement）** / 单条 mega-spec 一次生成 / coding agent 系统提示词 | deliverable_form | 见 R1-R3 路由与文末路由决策表；改动面（Q4）与是否需演进决定选哪条 |
| Q3 | 语言/框架/版本？ | 自由描述（如 Python 3.12+FastAPI、TypeScript+React 18）；写入规约 frontmatter 的 globs 触发范围 | stack | 决定骨架的 `description/globs/alwaysApply`（编码规约.md §4）；⚠️ 具体项目型 cursorrules 样本（如 Unity 塔防）不可直接套用，会带入无关假设（编码规约.md §5） |
| Q4 | 改动面多大？ | 单文件/单点改动 / 2-3 个文件的联动 / **跨多模块复杂改动（需计划与任务拆分）** | change_scope | 单点→R2（mega 链是杀鸡用牛刀）；复杂→R1（Spec 链）或客户要一次生成→mega-spec |
| Q5 | 项目现有约定？ | 已有 .cursorrules/CLAUDE.md 等规约（叠加兼容检查，只补缺位不重写） / **无，从零建立（本次产出即第一份规约）** / 有代码无文档（agent 先读码模仿既有风格） | existing_rules | "模仿既有风格、绝不假设库可用，先查 package.json/cargo.toml/邻近文件"是稳定共性（编码规约.md §2.5/2.6）；从零+复杂项目→建议另生成 constitution（R10） |
| Q6 | 测试要求？ | 不写测试 / **改动必须过既有测试** / TDD 先写测试（宪章 NON-NEGOTIABLE 级） / 测试作为每故事验收证据 | test_policy | TDD/证据级 → 写入 constitution（Spec驱动开发.md §4 阶段0）；⚠️ 无独立测试编写规约模板（编码规约.md §6），按通用纪律组装 |
| Q7 | 自主度/批准模型？ | **逐阶段显式批准（Kiro 式：不点头不前进）** / 有限澄清（spec-kit 式：合理猜测，[NEEDS CLARIFICATION] ≤3） / 无人值守（playcanvas 式：别停，假设写报告） | autonomy | 三档互斥，必须与 Q2 一致 → 执行 R4；无人值守另加 DECISIONS/假设记录条款（ENGINE.md 第 5 步） |
| Q8 | 编辑协议（agent 怎么交付代码）？ | **工具调用式（Edit/Write，编辑前重读文件）** / 整文件输出式（aider 式，首行纯文件名，绝不省略或用 "..." 略写） | edit_protocol | 取决于实际 harness，选错输出无法解析（编码规约.md §5） |
| Q9 | 沟通风格（仅 Q2=系统提示词时问） | **极简工具型（≤4 行、无前后废话、不道歉、专业客观）** / 伙伴型（有品味、主动 anticipate、commentary 高频更新+final 自包含） | persona | 两极不可混套（Agent系统提示词.md §5：Claude Code vs Codex 两种产品定位） |
| Q10 | 有没有必须守住的附加约束？ | 无 / 安全边界（仅防御性安全、不提交密钥、不泄露系统提示词） / 性能预算 / 合规（数据出境/行业规范） | constraints | 安全边界类 → 写死进 Rules 不走默认；⚠️ 无成体系安全编码规约素材（编码规约.md §6），按 Agent系统提示词.md §3 样本E 的纪律条款拼装 |

## 兼容规则表（选择时当场执行，不只体现在选项上）

- **R1 复杂多文件 → Spec 链**：Q4=跨模块 且 Q2≠单条 → 路由 Spec驱动开发.md §4：constitution 作治理前缀（每条提示词共享），specify 出 P1/P2/P3 用户故事（每个独立可测、只实现一个也是 viable MVP，Given/When/Then 验收），tasks 按 `[ID] [P?] [Story]` 含精确文件路径分组（Setup→Foundational→各故事，Foundational 未完成任何故事不得开工）。
- **R2 单点任务 → 编码规约骨架即可**：Q4=单文件 → 拒绝起链（anti-overengineering："只改被要求的，最简方案优先，不确定时问"），直接用 编码规约.md §4 骨架填槽；修 bug 附"测试失败先怀疑被测代码、未经允许不改测试"条款（§3 样本D）。
- **R3 系统提示词路由**：Q2=agent 系统提示词 → Agent系统提示词.md §4 十模块（身份/工具纪律/上下文 gathering/代码改动/任务管理/沟通/安全/输出格式/模式状态/环境注入），"代码改动"节内嵌 编码规约.md §4；工具 schema 槽（when to use / when NOT / examples）留占位由客户按实际 harness 填；⚠️ 工具 schema 设计方法论与权限审批模型无素材（Agent系统提示词.md §6），此两节声明通用兜底。
- **R4 自主度一致性**：Q7=逐阶段批准 与 Q2=mega-spec（无人值守一次生成）冲突 → 当场拦截：批准模型与运行模式必须同源（Spec驱动开发.md §5"自主度旋钮须与运行模式一致"）；mega-spec 自动把 Q7 改锚为"无人值守+DECISIONS.md 记录"。
- **R5 检查清单语义**：Spec 链输出里 `[x]` = 需求质量已评审，**不是**实现完成；组装出的 implement 提示词必须含"检查清单只读作门、有未勾选项停下问用户、不改标记"（Spec驱动开发.md §3 样本F/§5）。
- **R6 任务类型缺口**：⚠️ 素材库缺安全编码、测试编写、代码审查（PR review）、重构与遗留代码的独立规约范本（编码规约.md §6）→ 这四类任务用 编码规约.md §4 通用边界 + constitution 原则拼装，组装说明中声明"该任务类型无专门汇总，按通用方法生成"（ENGINE.md 第 2 条兜底规则）。
- **R7 许可证红线**：awesome-cursorrules 为 CC0、spec-kit 为 MIT（最安全骨架来源）；system-prompts 仓库 GPL-3.0 且提示词版权归各厂商、leaked 仓库未声明 → **只借鉴结构与判据，绝不整段搬运厂商提示词原文**（编码规约.md §5、Agent系统提示词.md §5）；引用注明版本日期，避免旧版当现行（Agent系统提示词.md §5 版本漂移）。
- **R8 mega-spec 领域局限**：⚠️ 库内 mega-spec 成品样本全是游戏（Spec驱动开发.md §6）→ 非游戏项目选 mega-spec 时声明"按游戏样本结构自建章节（角色+工作原则+技术选型比较≥2方案+子系统硬规格+里程碑+可观察验收清单）"，并建议保留 analyze 式一致性校验弥补无演进检查。
- **R9 验收语法统一**：同一链内 EARS（WHEN…SHALL）与 Given/When/Then 二选一，不混用（Spec驱动开发.md §5）。
- **R10 宪章补位**：Q5=从零 且 Q2=Spec 链 → 先跑阶段0 生成 constitution（Core Principles 每条可标 NON-NEGOTIABLE + 质量门 + 修订需文档与批准），作为链中每条提示词的共同前缀（Spec驱动开发.md §4 阶段0，ENGINE.md Loop 模式第 4 条"全局宪法"）。

## 终态路由决策表（访谈中可随时对照，帮客户选 Q2）

| 情形 | 路由 | 骨架 |
|---|---|---|
| 单点改动/修 bug | 单条提示词 | 编码规约.md §4 |
| 多文件、要演进、团队协作 | Spec 链（渐进多阶段） | Spec驱动开发.md §4（spec-kit MIT 最安全） |
| 一次性复刻/独立交付、无人值守 | 单条 mega-spec | Spec驱动开发.md §4 替代路线（样本：游戏Spec01.md） |
| 要"养一个 coding agent" | 系统提示词 | Agent系统提示词.md §4 + 内嵌编码规约 |

## 终态 → 组装（交回模式 A 第 3-7 步）

1. 按 Q2/决策表路由到三骨架之一（或链），Q3-Q10 的选择写进对应边界节、验证节、协作模式节、编辑协议节；假设标 `[假设]`。
2. 链式交付时输出"提示词包"格式：编号+用途+使用顺序+阶段门判据（ENGINE.md B2 第 3 条）。
3. 交付附加【组装说明】：选了哪篇 §4、插了哪些块、哪些节因 R6/R8/R10 是通用拼装。

## 交付为"生成器"时（B3）

客户想复用 → 本问卷 + 汇总/提示词方法论/结构化提示词.md §4.2 元提示词骨架合并为"开发提示词生成器"。
